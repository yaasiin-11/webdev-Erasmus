# Readiness

StudyHub on the free plans of Render (web service, Docker, Frankfurt) and Neon (Postgres,
Frankfurt). This file says what is live, how I know, and what is still weak.

## Live URL

https://webdev-studyhub.onrender.com (the same value is in `course.json` as `liveUrl`).

How to verify it:

- `GET /health` answers `{"status":"ok","db":"ok"}`. The `db` part runs a query, so it also proves the Neon connection works.
- `npm run readiness -- https://webdev-studyhub.onrender.com` runs the whole check below against the live site (health twice, 404s, broken JSON, security headers, a forbidden delete, the model feature, timings, brute force).
- `node checks/ex4.mjs` checks the live URL from `course.json`: it is https, `/health` returns 200 and the page has a real title.

How I checked: on 2026-11-24 `node checks/ex4.mjs` passed the live checks (https, `/health` 200, page served with the title "StudyHub: study groups and shared study sessions"). In the browser I signed in on the live site and asked for a password reset for my own account; the email arrived through Brevo.

The free web service sleeps after about 15 minutes without traffic. The first request after that takes up to about a minute (Render warns of 50 seconds or more); the readiness script prints the time of the first and second `/health` so this shows up.

## What happens when things fail

| What fails | What the user sees | Where it is handled |
|---|---|---|
| A page that does not exist | `public/404.html`, status 404 | static fallback |
| An API route that does not exist | `{"error":"Not found","code":"NotFound"}`, 404 | one error handler in `src/http` |
| Broken JSON in a request | 400 "The request body is not valid JSON.", no stack trace | same handler |
| No session | 401 "Sign in to continue." | auth middleware |
| Someone else's group | 403 "Only the person who created this group can delete it." | services, not routes |
| Neon unreachable | `/health` answers 503 `{"status":"error","db":"down"}`; screens show their error state with "Try again" | pool timeout of 5 s |
| Gemini slow, down or out of quota | the standard agenda template, labelled as a template | 8 s timeout, then fallback |
| Brevo down | the reset page still answers the same sentence; the failure goes to the log | mailer with an 8 s timeout |
| Google down or a wrong `state` | back to sign-in with a reason | `src/routes/auth.js` |
| Too many requests | 429 with a sentence that says what to do | in-memory limiters |

How I checked: the readiness script against a local server on 2026-11-24 for the 404s, broken JSON, 401, 403 and 429 rows (output below); the agenda and network failures with the Playwright script used for `docs/UI.md`. The full test suite also covers these answers: 107 tests pass.

## The four states of one screen

The groups list (`#/groups`), the screen everybody lands on after signing in:

- **Loading:** three skeleton rows with the height of real rows, `aria-busy="true"` on the list. They appeared 32 ms after navigating when the API was delayed by 1.5 s.
- **Empty:** "No group matches" when the search or filters find nothing, or "You are not in any group yet" with "Only my groups"; My sessions has its own empty state with a "Browse groups" button.
- **Error:** "The groups could not be loaded. StudyHub cannot be reached. Check your connection and try again." and a "Try again" button.
- **Success:** after "Join" the button becomes "Leave", the card says "You are a member" and a status line announces it, without reloading.

How I checked: each state forced with Playwright (delayed and aborted requests, a new account), screenshots in `docs/ui/groups-*.png`. Details in `docs/UI.md`.

## Request waterfall

Loading the groups page while signed in (Chrome, local server, cache warm):

1. `GET /` (the HTML page)
2. In parallel: `app.css`, two preloaded fonts and `main.js`
3. `main.js` imports `api.js`, `dom.js` and the six view modules in parallel; `group.js` then imports `chat.js` (one more hop)
4. `GET /api/auth/me` and `GET /api/auth/providers` in parallel
5. `GET /api/groups` after `me` answers

So there are three hops of JavaScript modules and two of API calls before the list is filled. Locally the page was ready in about 95 ms. On Render each hop costs a round trip to Frankfurt (I am in Sofia), so the module chain is what to fix first if it gets slow: bundle the modules, or add `<link rel="modulepreload">` for the views. The API calls are small: in the readiness run `GET /api/groups` took 14 ms and a group page 41 ms on the server.

How I checked: the Resource Timing entries of the page read with Playwright, and the "Request timing" part of the readiness script.

## Security

- **Headers:** `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self'; frame-ancestors 'none'` and more, `X-Content-Type-Options: nosniff`, and `Strict-Transport-Security` in production only (`src/http/middleware.js`).
- **Session cookie:** random token stored hashed in Postgres, cookie `HttpOnly`, `SameSite=Lax`, `Secure` in production, 7 days.
- **Passwords:** scrypt with a 16-byte salt; reset tokens and MCP tokens are stored as SHA-256 hashes, never in clear.
- **Cross-site requests:** a write sent from another site with a valid cookie is refused with 403 `CrossSite`.
- **Authorization:** every write route needs a session and the services check ownership: Boris deleting Ana's group gets 403 and the group is still there.
- **Brute force and abuse:** after 10 wrong passwords for one email the 11th attempt gets 429; 20 agenda suggestions per hour per person; 10 new accounts per address per hour; 30 chat messages per minute.
- **Google sign-in:** authorization code flow with `state` and PKCE (S256); unverified Google emails are refused.
- **Dependencies:** three runtime dependencies (`express`, `pg`, `pg-mem`); `npm audit` reports 0 vulnerabilities.
- **Least privilege for keys:** the Brevo key can only send transactional emails.

How I checked: the "Security" and "Brute force" parts of the readiness script (local run below), `npm audit` on 2026-11-24, and reading `src/http/middleware.js`, `src/routes/auth.js` and `src/services/authService.js`.

## Known gaps, ranked by risk

1. **Rate limits live in memory.** They reset when the free service restarts or sleeps, and would not be shared by two instances. Someone patient can try more passwords than the limit says. Fix: keep the counters in Postgres.
2. **Google sign-in only works for test users.** The OAuth consent screen is in Testing mode, so only accounts I add as test users can sign in with Google; everybody else must use email and password. Publishing the app needs Google's verification.
3. **Registration tells whether an email has an account** (409 on a taken email). The reset page does not leak it, but sign-up does.
4. **Cold start.** After 15 minutes without traffic the first request can take a minute. The UI shows loading states, but a first-time visitor may think it is broken.
5. **Free Gemini tier.** It has low per-minute limits (429) and, on the free tier, Google may use the requests to improve its products. The app falls back to the template, so nothing breaks, but the suggestion quality is not guaranteed.
6. **The Brevo key expires after 90 days without use.** If nobody resets a password for three months, reset emails stop until I create a new key.
7. **No backups beyond what Neon's free plan keeps**, and no monitoring except Render's logs.

How I checked: the first three come from reading the code and the self-review in `AGENT_LOG.md`; 4 to 6 from the Render, Google AI Studio and Brevo dashboards while deploying.

## The model feature in production

- **What it does:** "Suggest an agenda" asks `gemini-2.5-flash-lite` to split a study session into 3 to 6 timed blocks. The answer is checked (valid JSON, minutes add up to the length, titles cleaned) before the user sees it, and it is always labelled as an AI suggestion.
- **What data leaves the app:** only the topic the user typed, the group category and the length in minutes are sent to Google. No name, email, user id or group member is sent (AC-28), and the API key travels in the `x-goog-api-key` header, not in the URL. The topic is free text, so if somebody types personal data into it, that does leave.
- **Cost of one call:** the prompt is about 100 input tokens and `maxOutputTokens` is 800; a normal answer is around 150 to 250 tokens. At the list price of Gemini 2.5 Flash-Lite ($0.10 per million input tokens, $0.40 per million output tokens, list price on ai.google.dev as published on 2026-11-24) that is about $0.0001 per call and at most $0.00033. I am on the free tier, so I pay nothing.
- **When the provider is down:** the request has an 8 s timeout. A timeout, a 429 from the free quota, a 5xx or an answer that fails validation all give the standard template with a notice that says so ("The AI assistant did not answer in time…" or "The AI suggestion did not fit this session…"), and the cause goes to the log. The per-person limit of 20 suggestions per hour answers 429 with a sentence.

How I checked: read `src/services/agendaService.js` and `src/integrations/gemini.js`; the readiness script got the labelled fallback from `POST /api/agenda` locally (no key there), and the failure and thinking states were forced in the browser (see `docs/UI.md`). On Render `GEMINI_API_KEY` is set in the Environment tab.

## The MCP server in production

- **Where it runs:** not on Render. It is a stdio process started on the user's own machine with `npm run mcp`, and it connects straight to the same Neon database with `DATABASE_URL`.
- **Who may call the tools:** whoever holds a valid `MCP_TOKEN`. The token is created from the terminal with `npm run mcp:token -- <email>`, which needs the database URL, so only someone with access to the database can create one; it is printed once and stored as a SHA-256 hash. The website has no token page. Every call acts as that user, so the tools can do exactly what that user can do in the website and no more. `npm run mcp:token -- <email> --revoke` cuts access at once.
- **Tools:** `list_study_groups`, `get_group_schedule` and `create_study_session` call the same services as the HTTP routes, so the same rules apply (members only, no overlapping sessions, start in the future, 15 to 480 minutes). `find_lecture` and `list_lectures` only read `lectures.json`.
- **What it deliberately does not expose:** deleting groups or sessions, the chat, other users' data, and anything about accounts or passwords.
- **Weak point:** to use it against production the machine running it needs the Neon `DATABASE_URL`, which is a full database credential. Anyone who has it does not need the token at all. Fine for me as the developer, not something to give to users; the proper fix is an HTTP MCP endpoint on the web service that only takes the token.

How I checked: read `mcp-server/server.js`, `mcp-server/tools.js` and `src/services/authService.js`; the token rules are covered by tests, and `node mcp-server/check.mjs -- npm run --silent mcp` passes.
